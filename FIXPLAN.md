### Payment integrity (do these first)

- [x] **P1-1** 🔴 — **Stop trusting the client's amount.** `backend/src/routes/payments.ts:23,39` reads `amount` from `req.body` and passes it straight to `razorpay.orders.create`. The booking row is already fetched at `:29` and its `totalAmount` is never compared. **A user can pay ₹1 for a ₹5,000 event.** Use `booking.totalAmount`; ignore the body field entirely.
  > Changed: Deleted `amount` from the destructure entirely; charge is `Math.round(booking.totalAmount * 100)`. Verified live via temporary instrumentation: injected `amount:1` and `amount:999999` against a real booking, server computed 147500 paise (the real total) both times, ignoring the client value in both directions.
- [x] **P1-2** 🔴 — **Bind the Razorpay order to the booking.** Add `razorpayOrderId String?` to `Booking` (`schema.prisma:89-118`), store it in `create-order`, and assert `booking.razorpayOrderId === razorpay_order_id` in `/verify` (`payments.ts:62-109`). Without this, one valid ₹1 payment can be replayed to confirm unlimited bookings.
  > Changed: Added `razorpayOrderId String? @unique` + `paidAt DateTime?` (migration `20260824050000_add_razorpay_order_binding`). `create-order` persists the order id; `/verify` asserts it matches before writing. Verified with a forged-but-valid signature (secret pulled from `.env`): confirming booking A succeeds, replaying against a *different* booking B returns `400 "Payment does not match this booking"` and B stays unpaid in the DB — the exact cross-booking replay from the audit, reproduced and blocked.

  > Changed: Landed as part of P1-2 — `/verify` now requires `paymentStatus === 'unpaid'` via a conditional `updateMany`, and a same-booking replay of an already-confirmed payment returns 409 (verified live).
- [x] **P1-4** — Charge the platform fee. The client sends `price * guestCount` (`frontend/lib/stores/booking.ts:247`) while the server computed `totalAmount = ticketPrice + 25` (`backend/src/routes/bookings.ts:34-35`). **The ₹25 fee is never collected.** Resolved automatically by P1-1.

### Phase 4 Part 1 — Payments, capacity, schema, validation (2026-08-24)

*Goal: fix the payment gateway's three-way-broken webhook, the capacity race, six schema-hygiene items, the `evt-` client-priced-booking backdoor, the auth/me profile drop, `hostStatus` being ignored, and zod validation on 8 write endpoints. Branch `phase-4-part-1-payments-schema`. Read AUDIT.md §5 and §7 first — both pre-date Phase 1, so re-verified every claim against the current code before touching anything (several, e.g. "no `razorpayOrderId` column" and "client-controlled amount," were already fixed in Phase 1 and are not re-described here).*

**Webhook (P1-8→11)** — all three original defects fixed, plus the two missing event handlers: unconditional signature check (missing secret → 500, missing/bad signature → 400, replacing the old fail-open `if (webhookSecret && signature)`); `express.raw({type:'application/json'})` mounted on `/api/payments/webhook` specifically in `index.ts`, ahead of the global `express.json()`, so the HMAC is computed over the actual bytes Razorpay sent instead of a re-serialized (and therefore never-matching) object; the lookup now keys off `razorpayOrderId` instead of comparing a Razorpay `order_id` to a Prisma cuid. `payment.failed` → `paymentStatus: 'failed'` (needed the new enum value); `refund.processed` → looks up by `paymentId` and sets `'refunded'` + `refundId`. `errorMessage()` in `payments.ts` also got a real bug fix along the way: the Razorpay SDK rejects with `{statusCode, error: {description}}`, not an `Error` instance, so the existing `instanceof Error` check was logging the literal string `"[object Object]"` for every Razorpay API failure — added a fallback that reads `.error.description`.
> Verified live end-to-end, not just read: created a real paid booking, attached a test order id, and sent three signed `curl` requests against the running server — no signature (400), wrong signature (400), correct HMAC-SHA256 signature (200) — confirmed via `psql` that the booking flipped to `confirmed`/`paid` with the right `paymentId`/`paidAt`, and that `Event.attendees` incremented. Re-sent the same signed payload and confirmed the idempotency guard held (`matched 0 booking(s)` in the log, no double-write). Then hit a full event at exactly its capacity and confirmed a further booking attempt on it correctly 400s.

**Capacity race + orphaned seats (P4-3, P4-4)** — every read-then-write capacity check (`bookings.ts`'s create, `events.ts`'s `POST /:id/attend`) replaced with an atomic conditional `updateMany({ where: { attendees: { lt: capacity } } })`, so two concurrent requests on the last seat can't both read "available" before either writes. Booking creation wrapped in `prisma.$transaction`. The bigger structural change: `attendees` no longer increments at booking *creation* for paid events — only at *payment success* (`POST /verify`'s success path, and the webhook's `payment.captured` as the recovery path for when `/verify` never ran). Free events still reserve at creation, since they're confirmed+paid immediately and there's no later moment to do it at. This is what actually kills "abandoned checkout permanently holds a seat" — an abandoned paid checkout now never held one in the first place. Booking id pre-generated via `crypto.randomUUID()` so `qrCode` is set in the same `create()` call instead of an insert-then-update.
